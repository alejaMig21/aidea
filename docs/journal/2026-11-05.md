### 09:00 · pivot · The Tutor teaches; it has no autonomy over the project

Debating roles, the person fixed a principle: the Tutor exists to teach, as LearnHarness does, and the person acts. Whatever the Tutor wants to do it says or turns into a lesson; it never sends anything to a Builder and never changes a layer or a plugin by itself. The Contract became the Plan Mode of aidea for a whole project, a plugin of its own, and plugins can condition other plugins by what an action does and where, never by the kind of plugin.

**Why it matters:** it keeps the person in charge while letting plugins (and later several Builders) coexist: the rule is about actions, so a plugin written tomorrow is held the same way.
**Evidence:** `docs/adr/0009-the-tutor-teaches-and-the-contract-conditions-through-policies.md` · `.scratch/roles-and-contract/spec.md` · `.scratch/plugin-policies/spec.md`
**In their words:** "el tutor esta para aprender... el tutor no tiene autonomia sobre el proyecto. yo tengo autonomia"

### 10:00 · pivot · Languages are plugins, and the Tutor learns plugins from plugins

Asked whether the supported languages are plugins, the answer became yes: Python is the default one, TypeScript and JavaScript ship the same way, and any other language comes from a plugin a Builder writes. The way a language reaches each system follows what VS Code does (a variant per system, a program already on the machine, or a download with permission). In the same debate the Tutor was given a way to teach and test any plugin: a lesson, a read-only view of its state and named checks, required for plugins a Builder writes.

**Why it matters:** the set of languages stops being a list in the core, and the Tutor stops needing to know aidea's parts by name.
**Evidence:** `.scratch/language-plugins/spec.md` · `.scratch/plugin-lessons/spec.md` · `.scratch/plugin-teaching/spec.md`
**In their words:** "como funciona en VS Code el soporte para lenguajes? tratemos de hacer lo que ya funciona"

### 12:00 · surprise · Opening a big project was slow for a reason nobody had measured

Telegram took six seconds to open. Measuring showed the Python analysis walked every function's tree three times and every module's twice; walking each once, and keeping the whole analysis between openings, brought the analysis to 3.1 seconds and a second opening to 0.2. The Components overview then moved at 15 frames per second with the tests open, because 400 lines each had a transparency of their own and each arrowhead a marker; fading by stroke opacity and drawing arrowheads only where readable gave 36.

**Why it matters:** both costs were in the drawing and the repeated work, not in the size of the project; each fix was found by measuring the real one.
**Evidence:** commits `474dfff`, `803a2c8` · `.scratch/big-projects/issues/`

### 14:00 · pivot · Layers can be inferred for any project, with evidence

A blind exam (copies of two documented projects with their docs removed) showed that Architecture can be inferred well from the code, that Requirements are recovered only as behaviour, and that Business must never be guessed in a way that reads as an accusation. The design that followed: every claim cites files and lines and the core checks the citations; for a project of someone else the Tutor asks only for the person's learning goal and the layers are study notes.

**Why it matters:** aidea can serve a project that has no README without inventing a business for it.
**Evidence:** `.scratch/layer-inference/spec.md` · `.scratch/layer-inference-exam/`
**In their words:** "no me voy ni a molestar en leer todo porque leo la primera linea"

### 20:00 · pivot · The Tutor is rewritten as LearnHarness, and plugins give it the rest

After comparing the lesson cycle of LearnHarness with the Tutor's own, the person judged that most of the Tutor's features predated plugins that can be taught, and asked for a rewrite: one continuous conversation that measures what the person knows, shows a Plan and waits for the go-ahead, teaches one fact per step, and practises in sessions of its own. Helping to form the architecture or a Contract is then the Tutor using the plugins that own them. The person starts a Builder by writing in its chat, not with a card or a button; the Contract belongs to a plugin, and the Builders read it through tools plugins offer.

**Why it matters:** one method for everything about aidea, and no special case for the Contract; the Tutor and the Builders never talk to each other.
**Evidence:** `docs/adr/0010-the-tutor-is-the-learnharness-method-and-plugins-give-it-the-rest.md` · `.scratch/tutor-rewrite/spec.md`
**In their words:** "el plugin del tutor debe funcionar literalmente como lo hace learnharness"
