# DeepSeek Harness (`dsh`) and Creator mode

Researched 2026-11-04. Sources: the official repository, cloned shallow and read as source and docs, plus the GitHub API for releases. News and third-party guides were used only to find the repository and are not cited as proof. Claims marked "unverified" were not found in a primary source.

- Commit read: `8bd073392eef6f54e921a093b95076248eb08cbb`, dated 2026-11-03 15:27 +0800. Root `package.json` says version `0.2.2-alpha.3`.

## 1. What it is, layout, languages
- A product family, not one terminal agent. One runtime (`dsh`) is launched in named profiles: `web`, `headless`, `sdk`, `sdk-minimal`, `acp`. Source: [docs/architecture.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md), sections "Profiles and bundles" and "Application launch".
- Surfaces: a browser Web UI (`npx @deepseek-ai/dsh web`, default `http://127.0.0.1:3080`, per the [README](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md)); an Electron desktop app (`apps/desktop`, same architecture doc, section "Desktop application"); a one-shot `headless` profile; a JSON-RPC SDK server; an ACP server. No IDE extension was found in the root listing (not exhaustively checked).
- Language: TypeScript, Node `>=24.9.0`, pnpm workspace (root `package.json`). Also `python/` (SDK) and `native/system`. GitHub reports the repo language as TypeScript.
- Layout (root listing via GitHub API): `apps/` (`cli`, `desktop`, `desktop-host`, `plugin-market-generator`, `web`), `packages/` (about 55 groups, e.g. `core`, `llm`, `sandbox`, `guard`, `acp`, `sdk`, `extensions`, `client`, `preset`, `bundle`, `boot`, `subagent`), `python/`, `native/`, `vendor/`, `docs/`, `website/`, `benchmarks/`.
- Core idea: "Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself", built on the Cordis plugin framework (architecture.md, section "Cordis").
- Core packages and their `ctx` keys: `core/session` (`ctx.sessions`), `core/tools` (`ctx.tools`), `core/agent` (`ctx.agents`), `core/agent-loop` (`ctx.agentLoop`), `llm/llm` (`ctx.llm`) (architecture.md, "Core packages").

## 2. Plugin system and extension points
All names below are quoted from `packages/preset/agent-preset/skills/cordis-plugin-development/references/practices.md` unless stated.
- Tools: plugins register tools in the scoped registry `ctx.tools`.
- Intercept, pause or block tool calls: yes. `ctx.tools.guard()` "can only deny" (synchronous); `ctx.tools.restrict()` "can only remove tools"; the waterfall events `tools/pre-execute`, `tools/execute`, `tools/post-execute` "can rewrite". A decision that must wait for the user "returns `ask` from `tools/pre-execute`", which goes through `ctx.approval`. The full flow is drawn in [docs/tool-execution-pipeline.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-execution-pipeline.md): pre-execute, guards, approval, execute, post-execute, `tools/result`.
- Other events: `agent/pre-step`, `agent/request`, `llm/stream`, `agent/created`, `turn/end`, `assistant/message`; `fs/write-intent` and `fs/edit-intent` gate file mutations (pipeline doc).
- Prompt and context: `ctx.systemPrompt.section()`, `agent.inject()`, `agent.followup()`.
- UI: Web client plugins register React components into named slots with `ctx.slots.inject(...)` and `ctx.slots.register({ name, id, order }, Component)`. The shipped template uses the slot `conversation.composer.dock`; others named in the docs: `shell.overlay`, `conversation.chat.node`. A sidebar or panel slot was not enumerated in what I read (unverified which slot names exist for a sidebar).
- Commands: `ui-commands` exists under `packages/client`; its API was not read (unverified).
- Skills: `skill-filesystem` mounts `skills/` directories (agent-preset README).
- Hooks: a hooks system exists (session events `hook/invoked`, `hook/result` in the pipeline doc); its config format was not read (unverified).
- Storage: plugins keep config via a config editor and secrets via `ctx.credentials.modifyRecord()`. Per-session derived state uses `ctx.sessionProjections`. The doc says not to append new session event types, and `appendPluginRecord()` is "reserved for DSH's experimental packages". A free plugin database was not found.
- Background process or local server: a plugin's Host half is ordinary Node code (`index.js` exports `apply()`), so it can start anything Node can. `docs/user/guide/github-review.md` describes a plugin that mounts "a second WebServer". No restriction was found in the files read.
- Files: the Host half is not confined. Agent file tools are confined by `sandbox-policy` (below), plugin code is not.

## 3. How Creator mode builds a plugin
- Creator mode is one of the agent presets (Standard, Minimal, Creator). The official site says plugins can be created "through chat in Creator mode" (https://deepseek.com/en/harness/).
- Creator mode mounts four skills from `packages/preset/agent-preset/skills/`: `agent-experience`, `cordis-plugin-development`, `editing-cordis-compositions`, `cordis-composition-reference` (agent-preset README).
- Procedure in `cordis-plugin-development/SKILL.md`: inspect live APIs with the tools `cordis_inspect_list` and `cordis_inspect_query`; copy a template; write ordinary workspace files; then call the tool `plugin_manager` with `action: install_bundle` and the absolute package directory as `target`. "Changes affect every session in that profile and survive restart."
- Files written (template `templates/decoration/`): `package.json` (with a `dsh.bundle.patch` and `dsh.client` section), `cordis.patch.yml`, `index.js` (Host half, `export function apply() {}`), `client.js` (browser half, `window.__ModuleLoader__.load({ id, factory })`), `locale/*.json`, `icon.svg`. Language: plain JavaScript, React taken from the host module table.
- Loading: `install_bundle` installs with pnpm into the profile; it can go live through HMR (hot reload) or report `restart-required`.
- The five demos named in the task (3D viewer, paper reader, statistics page, video editor, theme), the date 2026-11-02 and the announcement text: not found in the repository; unverified. The mechanism above does match "describe a plugin, the Harness builds it", and the docs say UI requests with no other destination become "an installed UI plugin rendered in the Harness Web UI".
- The first commit date is 2026-08-13 (GitHub API `created_at`), so Creator mode is a feature of a three-month-old project, not a new product.

## 4. Permissions, sandbox, trust, marketplace
- Plugins are trusted code. `SAFETY.md`: the project "can execute model-generated code and commands, load third-party plugins, and access the network, processes, credentials, and files made available to it"; it "has not undergone a security audit and must not be treated as secure or production-ready"; sandboxing and approvals "do not guarantee isolation". I found no isolation of plugin code (no worker, VM or permission manifest) in the docs read.
- Agent actions are confined, not plugin code: `packages/sandbox/` has `sandbox-policy` (modes such as `read-only`, the fail-safe default, and `workspace-write`, plus `additionalWritableRoots`), `sandbox-local` and `sandbox-windows-acl`.
- Approval: installing and managing plugins goes through `plugin_manager`, whose actions "need approval without Full access" (SKILL.md). `approvedBuilds` for pnpm scripts needs explicit user approval.
- Marketplace: optional `plugin-market` package ("Custom plugin indexes" under Experimental plugins; read-only tool `plugin_market`). `packages/boot/plugin-market/README.md`: "Unsigned indexes - index content ... is the index's claim". No signing, no review. The desktop app "ships its exact dsh production runtime in signed resources" (that is app signing, not plugin signing).

## 6. ACP, SDK, headless driving
Yes, it can be driven by another program, three ways.
- ACP server: package `@deepseek-ai/dsh-acp`, started with `pnpm dsh --profile acp` ([packages/acp/acp/README.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/acp/acp/README.md)). JSON-RPC over stdio, standard ACP v1. Calls listed: `initialize`, `authenticate`, `session/new`, `session/list`, `session/resume`, `session/close`, `session/set_config_option`, `session/prompt`, `session/cancel`, `session/update`, `session/request_permission`.
- Limits that matter to aidea: the README calls it "automation-only"; it "intentionally omits DSH-specific presentation data and interactive UI features", "exposes only the standard ACP v1 surface"; "deletion, forks, transcript replay, and additional directories are unsupported"; config options are only `model` and `reasoning_effort`. No `session/set_mode` or `availableModes` appears in the contract table (so no modes). Permissions are answered by the client through `session/request_permission` (the README says "your client can answer automatically"). MCP servers can be attached per session. Whether it advertises `loadSession` or terminal capabilities was not checked.
- SDK: `packages/sdk/` ("newline-delimited JSON-RPC"; `protocol`, `client`, `server`); TypeScript client spawns `dsh --profile sdk`; Python SDK `deepseek-harness-sdk` in `python/` (sdk README, docs/user/guide/python-sdk.md). Observes session events, agent status, subagent completions.
- Headless: `dsh-headless` bundle, "a one-shot runner with no server".
- Reverse direction exists too: `packages/subagent/` has `subagent-acp`, `subagent-claude-code`, `subagent-codex`, so dsh can itself drive other agents. This is a client of agents, like aidea.
- The Windows path was not run; not tested. Nothing here was executed, only read.

## What this means for aidea
- (a) One more agent adapter: supported by evidence, with a cost. The ACP server is real, documented and matches ADR 0001's rule (aidea launches it as a child process and never writes its own loop). It speaks permissions and model selection, but it exposes no modes, no plan or todo cards, no fork or replay. aidea would get a plain prompt-and-permission agent. Also it is a developer preview with a release every few days; an adapter would need a pinned version. Not shown: that it runs well on Windows, or that quality with DeepSeek models fits aidea's work. A spike (`pnpm dsh --profile acp`, run `session/new` and `session/prompt`) would settle it.
- (b) Layers, Contract and Tutor as plugins of it: the evidence does not support this as a plan. Plugins are Cordis modules running inside the Harness process with full user trust; the UI plugin surface is slots in the Harness's own Web UI, and the product is the Harness's app. aidea is an Electron app with its own core server and ADR 0001 says the agent is a child process. Building aidea's pieces as plugins would invert that and tie them to an unstable, unaudited API. What the evidence does show is that the extension points aidea would need exist (`tools/pre-execute` with `ask`, `ctx.tools.guard()`, `agent.inject()`), so the idea is technically possible, only not advisable now.
- (c) Copy ideas from Creator mode: yes, cheap and supported. Useful ideas: the agent inspects live APIs before writing (`cordis_inspect_query`); the plugin is a small folder (manifest, patch, host half, client half) installed through one approved tool call; skills carry the procedure; a "weakest mechanism that suffices" ladder (`restrict`, `guard`, waterfall, prompt replace); and "the session log is the only source of truth", which resembles aidea's rule that state is derived. None of these needs the Harness code.
- Not established: the Nov 2 announcement text and demos, any plugin sandboxing roadmap, how stable the plugin API will be after the preview, and whether the web client slots include a sidebar.
