## 1. Run the whole project ("Play")
Raised 2026-10-31. Today the Run panel runs ONE function with test data (Playback; the core only starts the builder, the Python playback script and the Python environment lookup). Nothing starts a whole project. The name Run suggests it does. A modern IDE brings up the backend, the frontend and the rest by itself.
- DECIDED 2026-11-03: "the project is running" means its processes are alive (they started and have not exited). Not a port check, not a page. Consequence to settle later: a hung process counts as running, and "wait until the database is ready before starting the backend" cannot rest on this definition alone.
- Who decides HOW to start it: an agent that reads the project and orchestrates (flexible, costly, not repeatable), a run configuration written once (repeatable, needs someone to write it), or the hybrid in which the agent proposes the configuration once as a Proposal and the person keeps it? (The person suspects an agent may be "a missile for an ant".)
- DECIDED 2026-11-03: the hybrid. An agent reads the project ONCE and proposes the run recipe (commands, folders, order) as a Proposal; the person accepts or corrects it; from then on the project starts from the recipe with no agent. The person can ask the agent to review the recipe when the project changes. Reason: starting a project every day must cost no tokens and always start the same way, while writing the first recipe by hand is where a beginner gets stuck.
- DECIDED 2026-11-03: the recipe is a file inside the Project's `.aidea/` folder (for example `.aidea/run.json`), so it travels with the repository. Consequence: the Proposal flow and the guard that protects `.aidea/` must learn this new kind of file (the guard reports files outside the known set).
- DECIDED 2026-11-03: order PLUS a "ready" signal per part. The recipe says when a part counts as ready for the next one to start (for example a port that answers, or a line that appears in its output). This is a second notion, separate from "running" (processes alive): running is what the Play state shows, ready only gates the start order. Open: what happens when a part never becomes ready (a time limit, then say which part and why), and whether the agent that proposes the recipe also proposes each signal.
- DECIDED 2026-11-03: each part has a time limit to become ready (a default, for example 60 seconds, adjustable in the recipe). When a part exceeds it, Play stops everything it had already started and shows which part failed and the last lines it wrote; the part's tab keeps its text. Reason: a clean state after a failure (no loose processes, no busy ports) matters more than keeping processes alive, and a beginner can retry without hitting a busy port. Not chosen: leaving the started parts running, and waiting with no limit.
- DECIDED 2026-11-03: restarting one part also restarts everything that depends on it, in order, waiting for each "ready" signal. The person chose it for autonomy (aidea handles the consequences) even though it overlaps with "stop all" plus Play, and even though it restarts parts that did not need it (restarting the backend restarts the frontend). Open consequence: a quicker "restart only this part" may still be wanted later. Stop all: proposed, not contradicted, to stop in the reverse of the start order (front end first, database last); confirm when the interview resumes.
- DECIDED 2026-11-03: closing aidea while the project runs stops everything aidea started, after a warning ("a project is running, close and stop it?"). Nothing is reconnected on the next launch. Reason: closing aidea always leaves the machine as it was found; recognising processes from an earlier session is the most fragile part of the design and a failure leaves busy ports a beginner cannot free. Reconnecting can be added later as an option.
- Order and dependencies between parts (database, backend, frontend), waiting until each is ready, stopping all, restarting one: all decided above except the points marked open.
- DECIDED 2026-11-03: the processes and their output show in the terminal section (topic 3), not in the Run panel and not in a new Panel of their own. Consequence: Play cannot be built before the terminal section exists, so topic 3 is now a dependency of topic 1. The agent had recommended a separate Panel; the person chose the terminal.
- DECIDED 2026-11-03: the Panel that today is called Run (the Playback of one function, only available while a Flow is open) is renamed "Playback", the name GLOSSARY.md already uses for that feature. "Run" becomes the word for running the whole project, as in any IDE. The internal id `run` can stay, so saved Layouts keep working; the title, the Panels menu, GLOSSARY.md and the test that guards the retired names change.
- DECIDED 2026-11-03 (security): the person's permission is tied to the EXACT recipe accepted on this machine. aidea remembers which recipe was accepted; if the file is different for any reason (a pull, a hand edit, the Builder), Play shows the new recipe and asks for confirmation before starting anything. Same idea as the guard of `.aidea/` authored files. Why: Play cannot use Playback's sandbox (it must start processes, open ports and write files), and the recipe travels with the repository, so a cloned or pulled recipe could carry commands the person never saw. Not chosen: accepting once for good (a changed recipe would run unseen) and one permission card per command (defeats "Play").
- Security, still open: where the accepted-recipe memory lives (it must not live in the repository, or a pull could overwrite it), and what the confirmation shows (the whole recipe, or only what changed).

## 3. A terminal section
DECIDED 2026-11-03 (during topic 1): the first version only SHOWS. One tab per process that Play started, with its output, its state (alive or exited) and stop and restart buttons; nothing can be typed. It is built so that a second kind of tab, an interactive console, can be added later without redoing the first. The interactive console (and its native pseudo-terminal dependency and its security rule) stays open for a later interview.

DECIDED 2026-11-03 (option D, proposed by the person): BOTH the Tutor and the Builder can read the terminal's output. The flow the person wants: when something fails, the Tutor explains the cause to the person and the Builder then works knowing the cause; if the person already knows the cause, they skip the Tutor and tell the Builder directly, or let the Builder work out the cause by itself. Fit with the existing design: the Tutor already has read-only tools (`src/core/tutor-reads.ts`: the layers, one Node, the Project's files, a Playback recording), so a read-only tool for terminal output is the same kind and keeps Tutor story 26 true (it cannot run commands or change files).
DECIDED 2026-11-03: the reading is always started by the person, never by a mode. The person selects the error text in the terminal with the mouse and three buttons appear: "Explain" (the Tutor), "Fix" (the Builder) and "Explain and fix". The person rejected tying it to the Class and Direct modes (see topic 8). Fit: `src/ui/features/54-select.js` already shows a small control next to any selected text ("Just define", "Enter the Tutor"; the text only travels as data, limit 2000 characters), so this extends that control for terminal text.
DECIDED 2026-11-03: the vocabulary of the selection control is unified in the whole app. "Just define" is renamed "Explain" everywhere (the brief explanation); "Enter the Tutor" stays for the full class; "Fix" and "Explain and fix" appear only where fixing makes sense (the terminal and the Code panel). In the terminal the person therefore sees four buttons. The agent had recommended leaving the rest of the app unchanged; the person chose the unified naming. Touches `54-select.js`, its tests and GLOSSARY.md, and goes together with topic 8.
DECIDED 2026-11-03: no extra help for choosing the text. Terminals already print clear error text, so the person selects it and uses the buttons. The agent had proposed pre-selecting a guess or defaulting to the last lines; the person rejected both as unnecessary. Consequence: no heuristics per language.
DROPPED 2026-11-03: "how many fail-and-fix rounds". Every reading and every fix starts from a button the person presses, so there is no automatic loop to limit.
DECIDED 2026-11-03: the terminal has its own selection limit, higher (8000 characters) than the rest of the app (2000). When a terminal selection is longer, the END of the text is kept, not the start, because the useful part of a traceback is last; the control tells the person the text was cut. Reason: errors are long in terminals and short elsewhere. Cost accepted: two limits to maintain. Not chosen: keeping 2000 with a warning, and 8000 everywhere (more tokens per click in every Panel).
DECIDED 2026-11-03 (security): warn, do not hide. When the selected terminal text looks like it contains a secret (a long key, `password=`, `token=` and similar), the control shows "this looks like a secret" and asks for confirmation before sending it to the Tutor or the Builder. The text is never altered. Hostile text stays covered by the rule that selected text travels only as data, never as an instruction. Cost accepted: pattern rules miss some secrets and flag some harmless text. Not chosen: sending with no check, and hiding detected secrets automatically (it could hide the very value that explains the error).
DECIDED 2026-11-03: the terminal is a normal Panel with its initial place in a new strip at the bottom, full width, like Visual Studio and VS Code. The person may move it, and the saved Layout remembers where it was left. Consequence: the Layout registry (left and right sides only today) must learn a bottom zone, and the default arrangement loses some Canvas height. Reason: terminal lines are long and a narrow column breaks them.
DECIDED 2026-11-03: the interactive console is built AFTER version 1, like the one in VS Code: a normal console where what the person types runs under their own responsibility. The agent had recommended not promising it; the person chose to build it later. Correction of an earlier claim: the native pseudo-terminal piece is compiled once by aidea's own build for each operating system it ships on, as VS Code does; it is not compiled per user project, so it costs the maintainers a build step, not the person using aidea. Still open for that later work: whether ADR 0003 gets an exception for this one dependency, and the exact packaging step.

Original notes: A Panel to run commands and watch processes. Shell in the Project folder; relation to the Builder's permission cards and to topics 1 and Run; a native pseudo-terminal dependency (ADR 0003 asks for no new dependency without a reason); what the person sees of processes aidea started.

## 8. The Class and Direct modes of the Builder
Raised 2026-11-03. The person has never liked them and says that what each mode does is not understandable. Today (Tutor spec stories 21 and 23) Class makes the Builder stop at each Blocking decision until a short class is answered, and Direct lets it work without stopping. Questions: what problem do the modes solve for the person, is a mode switch the right control at all, would the choice be better made at the moment it matters (as with the three buttons chosen for a failed part), and how are the names and the explanation changed if the switch stays. Affects the Builder panel, the Tutor spec and GLOSSARY.md.
DECIDED 2026-11-03: the per-Project switch is removed. At a Blocking decision the Builder stops and shows a card in the chat with two buttons, "Explain first" (the Tutor's short class) and "Go ahead". The choice is made each time, not as a setting. Cost accepted: one extra click when the person already knows what they want. Not chosen: never stopping (a card with an optional Explain button) and dropping the decision classes altogether. Consequence: Tutor spec stories 21 and 23 and the "Class mode" and "Direct mode" entries of GLOSSARY.md must be rewritten; the Builder panel loses the switch.
CORRECTION 2026-11-03 (after the person asked what happens in auto mode, and after reading `src/core/decision-class.ts`): Class mode never pauses the Builder or touches its Permission mode. It marks a new Proposal as `held`: the person cannot accept it until a decision class is answered or skipped ("Decide for me" = `skipClass`, which records the skip as Evidence and lets the Proposal be accepted as the Builder wrote it). So Class and the agent's Permission mode are independent, and a change of modes in Claude Code or a new agent changes nothing here, because modes arrive from the adapter as data. The wording "stops the builder" in GLOSSARY.md and the Tutor spec is what misleads. Whether the Builder itself waits on a held Proposal is NOT verified. The person also ruled out a custom agent: it has nothing special over Claude Code, so ADR 0001 (no own agent loop) stands; the research in `.scratch/harness/research/01-harness-landscape.md` stays as background only. FINAL DECISION 2026-11-03 (supersedes the card with "Explain first" and "Go ahead"): Class mode, Direct mode and the decision classes are removed altogether. Reason, in the person's words: the Builder is the builder and the person with the Tutor is the architect. The Contract (the Business, Requirements and Architecture layers) is agreed by the person and the Tutor and handed to the Builder, who has autonomy to carry out the task but must not invent anything; it takes no important decision that is not already in the Contract. So there is no Blocking decision to teach. When the person does not understand something the Builder wrote or did, they select the text and ask the Tutor with the existing selection control. A change that is not in the Contract still reaches the person only as a Proposal, as the Contract definition already says. Consequences to implement: delete the Class/Direct switch (`35-agent-options.js`, `classMode` in `agent-options.ts` and `preferences.ts`), `src/core/decision-class.ts` and its tests, `held` and "Decide for me", the Tutor spec stories 21 and 23 and the entries Class mode, Direct mode, Decision class and Blocking decision in GLOSSARY.md; the Builder must be told in its prompt to follow the Contract and not invent. Still open: how a Proposal for something the Contract lacks is worded to the person.
