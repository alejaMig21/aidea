# Everything is a plugin: interview decisions

Started 2026-11-04. Source of the questions: `.scratch/plugins/research/01-deepseek-plugin-philosophy.md` (section 17). The person answers one question at a time; each decision is recorded here. Background: `.scratch/future/interviews-pending.md` (REVISED section) and ADR 0001.

## 1. The kernel
DECIDED 2026-11-04: aidea has a small real kernel that is NOT a plugin (option A, as the agent recommended). The kernel is: the plugin loader and the registry of what plugins offer; the plugin manager (quarantine, install, remove, enable, disable, and a safe mode that starts with every third-party plugin off); the window with the Layout and the named slots where plugins put things; the point that decides on guards (plugins contribute rules, the kernel decides); configuration, credentials and the core server; a minimal emergency screen to see and switch off plugins. Everything else (Panels, layers, language adapters, the Tutor, agent adapters, tools, guard rules, Playback, the terminal) is a plugin shipped with aidea on the same API as an installed one. Not chosen: no kernel at all, as DeepSeek does (a broken plugin could leave no way to switch it off), and a larger kernel with the basic Panels in it.

## 2. Built-in plugins
DECIDED 2026-11-04: the plugins that ship with aidea can be removed like any installed one, except a few marked required (for example the agent adapter and the emergency screen). Removing one that another plugin needs leaves that other plugin inactive and aidea says why instead of breaking (option A, as the agent recommended). Not chosen: removable without exception, and shipped plugins that can only be switched off.

## 3. The API version and the promise
DECIDED 2026-11-04: one version of the public API for the core and the interface together. While the major number does not change, a plugin keeps working; when a new major version appears the previous one is kept for a fixed time (for example 12 months). A plugin that asks for a version aidea does not offer is shown as "incompatible" and does not activate, without breaking anything. Before aidea version 1 the API may change with notice (option A, as the agent recommended). Not chosen: two separate versions, and no promise as DeepSeek has.

## 4. The format of a plugin
DECIDED 2026-11-04 (by the agent; the person had no preference and said they did not know what is more comfortable for the people who write plugins): a plugin is delivered as plain, finished JavaScript in a folder with a manifest. Any library it uses is bundled into its folder beforehand. Nothing is installed at activation, there are no install scripts, and native binaries are not allowed unless the manifest declares them, in which case the scanner flags them. Reason: the main author will be the Builder writing small plugins from a description (as in Creator Mode of the DeepSeek Harness), which needs no build tool; and the quarantine can read exactly what will run. Left open and compatible with this choice: later, building from source inside a Docker container (only when Docker exists) can produce this same folder, and a container can serve as an optional behaviour scan. Not chosen now: an install step on the person's machine, and compiling TypeScript inside aidea.

## 5. Where the interface of a plugin is drawn
DECIDED 2026-11-04: in the same window as aidea, with aidea's look (the shared scale of sizes and colours), not in an isolated frame (option A, as the agent recommended). Reason: an installed plugin already runs with the person's permissions in the core, so isolating only its drawing would protect nothing real; the protection is the quarantine before installing. Not chosen: an isolated frame.

## 6. What the scanner does with a finding
DECIDED 2026-11-04: some findings block and others only warn (option A, as the agent recommended). Blocking findings: obfuscated code, install scripts, hidden binaries, and doing something the manifest does not declare (for example using the network without saying so). The person can install anyway, only after a confirmation that names each blocking finding. Warnings: capabilities the plugin declared and uses (network, files). The screen must say that a scan lowers the risk and does not prove a plugin is safe. Not chosen: nothing blocks, and every finding blocks with no way past it.

## 7. Updates
DECIDED 2026-11-04: every update, even a small one, goes through the quarantine, but it is compared with the version the person accepted, and the scanner shows only what changed (new files, new capabilities, new findings). If nothing serious changed it is one click (option A, as the agent recommended). Not chosen: skipping the review for small updates, and a full scan from zero for every update.

## 8. Settings and data of a plugin
DECIDED 2026-11-04: each plugin has a private folder by its name, outside any Project; its settings are declared with a schema in the manifest and drawn as a form; secrets go to the operating system's secure store, never to a settings file. When the person removes a plugin, aidea asks, with "keep" as the default, whether to delete its data too (option A, as the agent recommended). Not chosen: always delete, and always keep.

## 9. Roles have instances, and each instance picks its provider
DECIDED 2026-11-04 (the person's answer replaced the agent's "one active per role" proposal): a role such as the Tutor or the Builder is not "one active plugin". The person can create SEVERAL instances of a role, and each instance connects to its own provider. A role needs at least one instance. Providers are plugins (adapters): for example Claude Code, a DeepSeek one, Codex, Kimi. Examples the person gave: two Tutors at once (opening a second class on something the first Tutor mentioned without breaking the first class); four Builders working at once, each on its own git branch, collaborating on a set of complex tasks; a DeepSeek Tutor next to a Codex Tutor; a Claude Code Builder next to a Kimi Builder. This is a stated future goal for the degree of freedom, not for version 1. Consequences to design later: every instance is its own session; Builders that work in parallel need a branch (a git worktree) each; the Contract, the guard and Proposals must cope with several writers; the existing adapter-per-role setting becomes instances. Open: which services stay single-instance (for example the language adapter of one language), and how parallel Builders are coordinated.

## 10. Guard rules from plugins
DECIDED 2026-11-04: a plugin may only TIGHTEN: it can answer "no" or "ask the person", never "let it pass" against another rule; if any rule says no, it is no (option A, as the agent recommended, the model of the DeepSeek Harness). So no plugin, not even a malicious one, can remove a protection aidea already has; it can only add more. Not chosen: loosening with a confirmation each time, and free rules.

## 11. Who uses the plugin manager
DECIDED 2026-11-04 (option A, "for now"): only the person installs, enables and removes. The Builder and the Tutor can write a plugin into the quarantine folder and PROPOSE installing it: that opens the manager screen with the scan result, and the person confirms there. A plugin can never install another plugin. Not chosen for now: the agent installing after a permission card (the card does not show the scan), and plugins installing plugins. DIRECTION stated by the person: aidea should move toward a state where agents can do EVERYTHING in the app. Design rule that follows (from the DeepSeek digest, user-actions): implement each operation ONCE as a service of the kernel or of a plugin, so the interface and the agents call the same thing; an action that grants or confirms authority (installing code, accepting a Proposal) stays with the person unless the person decides otherwise later.

## 12. How aidea gets from today to the kernel and plugins
DECIDED 2026-11-04: step by step, never leaving aidea unusable (option A, as the agent recommended). After version 1: first the kernel and the plugin API; then the existing features become built-in plugins one at a time, starting with the ones closest to it (the Panels Terminal, Files and Code already live in the Panel registry), with the app working after each step and the existing tests kept. Old code and plugins live side by side for a while. Not chosen: rewriting everything at once, and only new things being plugins.

## 13. Creator Mode from the first version
DECIDED 2026-11-04: the first version of the plugin system includes both the plugin-writing skill (instructions that let an agent write a plugin well: start small, look at the live app, copy a template) and the live inspection (a read-only query of the services, slots, settings and style tokens the running app offers), so the Builder can create plugins from the first day (option A, as the agent recommended). Not chosen: later, and inspection only. The agent writes the plugin into the quarantine folder; installing stays with the person (decision 11).

## 14. Events defined by plugins
DECIDED 2026-11-04: a plugin may define its own events (option A, as the agent recommended). Each carries the name of the plugin that defines it, declares whether it only announces or can also ask for a decision, and is part of that plugin's public contract, versioned; the live inspection lists them. This is what lets a plugin build on another (the Data layer on Playback, the versions plugin on the animation engine). Not chosen: only the kernel defines events, and free events with no rules.

## 15. A marketplace later
DECIDED 2026-11-04: a marketplace is wanted later, under today's rules (option A, as the agent recommended). A plugin from it goes through the same quarantine and scan as any other; the marketplace helps find plugins, it does not make them trusted, and nothing installs by itself. Not chosen: never, and marketplace plugins trusted without quarantine.
